# Troubleshooting: CI Failure Quick Lookup

*A symptom-first index into this repo's real, dated CI incidents. [`ci-workflows.md`](ci-workflows.md) tells the story of each pattern and why it happened; this document exists for the moment you're staring at a red run and want the fastest path to "is this my fault." Find what you're seeing on the left, get the likely cause and where to read more on the right. Every row links to a real, verified, dated fix, not a hypothetical.*

## By symptom

| What you're seeing | Likely cause | Read more |
|---|---|---|
| A `workflow_dispatch` or manually-triggered run shows red, but the same commit's push-triggered run passed (or vice versa) | Concurrency group collision, the group key resolved identically for both trigger types and `cancel-in-progress` killed one of them | [Pattern A](ci-workflows.md#pattern-a-concurrency-group-too-coarse-dispatch-collides-with-push) |
| A `workflow_call`'d reusable workflow's badge looks wrong for its own run | Same as above, `${{ github.workflow }}` inside a `workflow_call` resolves to the *caller's* name, not the callee's, so two different workflows silently share one concurrency group | [Pattern A](ci-workflows.md#pattern-a-concurrency-group-too-coarse-dispatch-collides-with-push) |
| A preview/dev deploy shipped, but the corresponding validate workflow is showing (or showed) a failure | Deploy and validate ran independently in parallel with no `needs:` gate between them | [Pattern B](ci-workflows.md#pattern-b-deploy-shipping-ahead-of-or-despite-a-failed-validation) |
| A README badge is stuck red/stale even though the underlying bug was already fixed and merged | The workflow that drives the badge has a path filter that doesn't cover the file that actually changed, so it never re-ran | [Pattern B](ci-workflows.md#pattern-b-deploy-shipping-ahead-of-or-despite-a-failed-validation), StaffML 2026-06-16 entry |
| `ModuleNotFoundError` or `ImportError` in a CI-only step, but the code runs fine locally or in the actual product | A CI test/smoke step imports a pre-refactor path, or depends on a package that was never added to the manifest CI actually installs from | [Pattern C](ci-workflows.md#pattern-c-ci-catching-drift-between-what-code-assumes-and-what-actually-changed) and [Pattern E](ci-workflows.md#pattern-e-a-check-that-ci-never-actually-runs-so-drift-accumulates-silently) |
| `micropip`/Pyodide 404s fetching a wheel, or `BadZipFile: File is not a zip file` in a WASM smoke test | A wheel the lab/notebook actually needs was never built or copied into the path the test stages | [Pattern C](ci-workflows.md#pattern-c-ci-catching-drift-between-what-code-assumes-and-what-actually-changed), Labs 2026-06-15 entry |
| A circular-import error that only reproduces in CI, never locally | Check the Python version CI pins, 3.11 has a real interpreter bug re-entering partially-initialized packages on relative imports that 3.12 (PEP 690) fixed | [Pattern C](ci-workflows.md#pattern-c-ci-catching-drift-between-what-code-assumes-and-what-actually-changed), MLSys·im 2026-05-27 entry |
| A `pre-commit` hook fails in CI but passes locally, or fails with a missing-module error for a package you know is installed | `pre-commit`'s fallback dependency list (used when its own environment resolution can't reach the network) is a second, easy-to-drift source of truth from the real dependency list | [Pattern C](ci-workflows.md#pattern-c-ci-catching-drift-between-what-code-assumes-and-what-actually-changed), MLSys·im 2026-05-26 entry |
| A CodeQL alert about missing or overly broad `permissions:` on a workflow | The workflow never declared an explicit `permissions:` block and defaulted to the repo-wide token policy | [Pattern D](ci-workflows.md#pattern-d-permissions-and-shell-quoting-mistakes), StaffML 2026-05-01 entry |
| A shell step fails immediately after a Python heredoc, with an error on an unrelated-looking `(` or similar character | An f-string or embedded string inside the heredoc used the same quote character as the outer shell string, closing it early | [Pattern D](ci-workflows.md#pattern-d-permissions-and-shell-quoting-mistakes), StaffML 2026-04-28 entry |
| A deploy validation step fails checking for `<page>.html`, but the actual build output looks correct when you check it by hand | The check assumes flat HTML paths, but `trailingSlash: true` (Next.js) or an equivalent config emits `<page>/index.html` instead | [Pattern D](ci-workflows.md#pattern-d-permissions-and-shell-quoting-mistakes), StaffML 2026-04-29 entry (issue #1600) |
| A bot/automation step (auto-crediting, auto-labeling) returns 403 posting a comment, only on fork PRs | The default `pull_request` trigger delivers a read-only `GITHUB_TOKEN` to fork PRs no matter what `permissions:` the workflow declares; needs `pull_request_target` (only safe if the workflow never checks out fork code) | [Pattern D](ci-workflows.md#pattern-d-permissions-and-shell-quoting-mistakes), repo-wide 2026-05-01 entry |
| `mlperf-edu`'s CI is red on a PR that doesn't obviously touch anything CI-related | Almost certainly the known, still-unfixed missing-`matplotlib` gap, or the hardcoded workload-count assertion, not your change | [Pattern E](ci-workflows.md#pattern-e-a-check-that-ci-never-actually-runs-so-drift-accumulates-silently), [`mlperf-edu/ci-workflows.md`](mlperf-edu/ci-workflows.md) |
| `npm run lint` crashes with a cryptic rule-loading error in StaffML | Check the pinned `eslint` version against what `eslint-config-next`'s nested `eslint-plugin-react` actually supports as a peer, this exact mismatch already happened once | [Pattern E](ci-workflows.md#pattern-e-a-check-that-ci-never-actually-runs-so-drift-accumulates-silently), [`staffml/ci-workflows.md`](staffml/ci-workflows.md) |
| A Dependabot PR for `dompurify`, `mermaid`, or `linkify-it` in `socratiq` looks correct but something feels off about what actually ships | The manifest bump alone is not enough, SocratiQ ships as a committed pre-built `bundle.js`, and it must be regenerated in the same PR or the live widget keeps the old vulnerable/outdated code regardless of what `package.json` says | [`socratiq/ci-workflows.md`](socratiq/ci-workflows.md), and section 5 of the top-level doc |
| A Dependabot PR for `wrangler` or `@cloudflare/workers-types` in one StaffML Worker only | Both Cloudflare Workers (`staffml-vault-worker` and the AI interviewer worker) pin these identically on purpose, bumping one without the other creates version drift between them | [`dependency-map.md`](dependency-map.md) section 4, PR #1965's review comment |
| A Python dependency floor bump in `mlsysim` or `labs` breaks the WASM export smoke test | Pyodide/`micropip` can only install pure-Python wheels and lags behind PyPI, a floor raised past what Pyodide currently bundles is uninstallable in the browser even though it's a perfectly valid PyPI release | Real examples: numpy `>=2.2.6` and PyYAML `6.0.3`, both closed for this reason |
| `design-grammar` or `socratiq` PRs pass CI but you're not sure what was actually checked | `design-grammar` has no CI validation of any kind, its own `npm run validate` exists but nothing runs it. `socratiq` has exactly one workflow, a bundle-drift guard, not a full validate/deploy pipeline | [`design-grammar/ci-workflows.md`](design-grammar/ci-workflows.md), [`socratiq/ci-workflows.md`](socratiq/ci-workflows.md) |

## If none of these match

Check the terse multi-commit cluster from 2026-06-20 to 2026-06-23 (`02996dcb1c`, `855803df04`, `52906be2d8`, `0b98b740eb`) in [`ci-workflows.md`](ci-workflows.md#a-cluster-worth-knowing-about-but-not-fully-detailed-here) if the failure touches `infra-cloudflare-purge.yml` or a `publish-live.yml`'s site-only deploy path, it reads like a real incident under time pressure even though the commit messages are too terse to fully reconstruct.

Otherwise: `git log --full-history -- .github/workflows/` is the actual source these patterns were mined from, `git log -p -S"<distinctive string from the error>" -- .github/workflows/` is the fastest way to find whether a similar failure has already been fixed once before.
